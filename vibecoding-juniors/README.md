# «Вайбкодинг убивает джунов?»

Аналитическая записка по выборке вакансий hh.ru (85 086 вакансий, январь 2023 —
июнь 2026).

**Автор:** Калошкина Светлана.
**Дата:** 2026-09-19.

## Задача 

Проверить причинное утверждение «вайбкодинг убивает джунов» на выборке IT-вакансий
hh.ru через квазиэксперимент разница-разниц: сравниваем изменение доли джуновских
вакансий в ролях, где основной продукт это код, который умеет генерировать LLM
(разработчик, тестировщик, DevOps, тимлид разработки), против ролей, где это не так
(техподдержка, сисадмин, дизайн, ИБ и т. п.), до и после начала заметного роста
упоминаний ИИ-инструментов в вакансиях (2025-02).

## Рекомендую начать с аналоитической записки

`report/report.pdf` — аналитическая записка (4 страницы). Основной результат.

## Как повторить анализ (три команды)

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python3 src/00_download.py && python3 src/01_prepare.py && \
  python3 src/02_descriptive.py && python3 src/03_did.py && python3 src/04_robustness.py
```

Либо тот же результат из `notebook.ipynb` (Cell → Run All) — ноутбук вызывает те же
пять скриптов и дополнительно показывает итоговые таблицы/рисунки инлайн.

`data/` создаётся скриптами автоматически. Данные качаются один раз: повторный
запуск `00_download.py` не скачивает файл заново, если он уже есть.

## Время прогона

Проверено чистым прогоном (папки `data/` и `output/` удалены заново, каждый
скрипт запущен отдельным процессом, засечено по шагам):

```
00_download.py   : 20 с  (сеть, скачивание 57 МБ — основной источник разброса времени)
01_prepare.py    :  3 с
02_descriptive.py:  1 с
03_did.py        : 10 с
04_robustness.py : 43 с (27 регрессий в Т6 + модель Т7 с ~5,2 тыс. работодателей)
-----------------------------------------------
ИТОГО            : 77 секунд
```

В разных прогонах итог колебался от 68 до 131 секунд — разброс почти целиком из-за
сетевой задержки скачивания 57 МБ и загруженности машины в моменте, не из-за
самого расчёта (шаги 01–04 стабильно укладываются в ~55–60 с). Если `data/`
уже скачана (например, при повторном запуске из `notebook.ipynb` в той же сессии),
шаг скачивания пропускается и итог короче — эта разница видна и в самом ноутбуке.

Замерено на машине с 20 ядрами CPU и 15 ГБ RAM без GPU. По ядрам это в 2,5 раза
больше требуемых 8; по памяти — на 1 ГБ *меньше* заявленных в задании 16 ГБ (это не
опечатка, машина слабее по этому параметру), но пиковое потребление памяти в
пайплайне не превышает нескольких сотен мегабайт (файл 58 МБ на диске, ~240 МБ в
памяти после разбора, самые тяжёлые регрессии — на ~70 тыс. строк и ~60 дамми-
столбцов), так что запас по памяти в любом случае большой. Решающий запас — по
времени: 77 секунд против лимита в 1800 секунд (30 минут), с многократным
избытком даже на вдвое более медленном железе. Установка зависимостей
(`pip install -r requirements.txt`, около минуты) в этот расчёт не входит, как и
оговорено в задании.

## Что проверено и сходится

- Ручной DiD по четырём средним **точно** совпадает с коэффициентом при
  взаимодействии в регрессии без FE (математическое тождество, проверено
  кодом — см. столбец `note` в `T5_did_summary.csv`, `совпадение: True`).
- Сумма компонент shift-share сходится с наблюдаемым изменением доли
  джунов с точностью до `1e-9` (арифметическая проверка в `02_descriptive.py`).
- Плацебо-тест (фиктивная дата 2024-02 на выборке, обрезанной до 2025-01)
  даёт оценку −0,9 п.п., статистически неотличимую от нуля (p = 0,42).
- При поочерёдном исключении любой из 14 ролей группы code/noncode знак
  основного эффекта (отрицательный) сохраняется во всех 14 случаях.
- Из 22 проверок устойчивости в `T6_robustness.csv` (плацебо, три даты
  отсечки, два состава групп, два региона, 14 исключений ролей) эффект
  сохраняет отрицательный знак во всех 22. Ещё 5 строк таблицы — не
  проверки устойчивости, а отдельные результаты: базовая спецификация
  (1 строка), декомпозиция по сегментам опыта (2 строки, знак разный по
  сегментам — см. записку) и проверки на предтренд (2 строки, см. ниже).
- **Оценка НЕ устойчива к допущению группового линейного тренда**: при
  добавлении `code:t` к основной спецификации эффект падает с −2,9 до
  −1,0 п.п. и теряет значимость (p≈0,50) — см. «Правки по итогам первой
  самопроверки» выше и записку, раздел 4. Это единственное допущение,
  которое основная спецификация не переживает.
- Число строк в `analysis.parquet` совпадает с исходным (85 086), ни один
  из флагов джуна и групп ролей не имеет пропусков.
- Полный прогон с нуля в чистом окружении завершился без единой ошибки и
  без ручного вмешательства (см. раздел «Время прогона» выше).
