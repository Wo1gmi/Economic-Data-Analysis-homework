# «Вайбкодинг убивает джунов?»

Аналитическая записка по выборке вакансий hh.ru (85 086 вакансий, январь 2023 —
июнь 2026).

**Автор:** Калошкина Светлана.
**Дата сборки:** 2026-09-19.

## Задача одной фразой

Проверить причинное утверждение «вайбкодинг убивает джунов» на выборке IT-вакансий
hh.ru через квазиэксперимент разница-разниц: сравниваем изменение доли джуновских
вакансий в ролях, где основной продукт — код, который умеет генерировать LLM
(разработчик, тестировщик, DevOps, тимлид разработки), против ролей, где это не так
(техподдержка, сисадмин, дизайн, ИБ и т. п.), до и после начала заметного роста
упоминаний ИИ-инструментов в вакансиях (2025-02).

## Что почитать в первую очередь

`report/report.pdf` — аналитическая записка (4 страницы). Это основной результат.

## Время прогона (критерий K9)

Проверено чистым прогоном (папки `data/` и `output/` удалены заново, каждый
скрипт запущен отдельным процессом, засечено по шагам):

```
00_download.py   : 20 с  (сеть, скачивание 57 МБ — основной источник разброса времени)
01_prepare.py    :  3 с
02_descriptive.py:  1 с
03_did.py        : 10 с
04_robustness.py : 43 с (27 регрессий в Т6 + модель Т7 с ~5,2 тыс. работодателей)
-----------------------------------------------
ИТОГО            : 77 секунд
```

В разных прогонах итог колебался от 68 до 131 секунд — разброс почти целиком из-за
сетевой задержки скачивания 57 МБ и загруженности машины в моменте, не из-за
самого расчёта (шаги 01–04 стабильно укладываются в ~55–60 с). Если `data/`
уже скачана (например, при повторном запуске из `notebook.ipynb` в той же сессии),
шаг скачивания пропускается и итог короче — эта разница видна и в самом ноутбуке.

Замерено на машине с 20 ядрами CPU и 15 ГБ RAM без GPU. По ядрам это в 2,5 раза
больше требуемых 8; по памяти — на 1 ГБ *меньше* заявленных в задании 16 ГБ (это не
опечатка, машина слабее по этому параметру), но пиковое потребление памяти в
пайплайне не превышает нескольких сотен мегабайт (файл 58 МБ на диске, ~240 МБ в
памяти после разбора, самые тяжёлые регрессии — на ~70 тыс. строк и ~60 дамми-
столбцов), так что запас по памяти в любом случае большой. Решающий запас — по
времени: 77 секунд против лимита в 1800 секунд (30 минут), с многократным
избытком даже на вдвое более медленном железе. Установка зависимостей
(`pip install -r requirements.txt`, около минуты) в этот расчёт не входит, как и
оговорено в задании.

## Отклонения от плана

План (`plan_vibecoding.md`) — рабочий документ разведки данных, часть цифр в
нём черновая. Ниже перечислены места, где собственный код (Э2–Э8) разошёлся
с планом, и почему.

1. **Пробел в классификации ролей.** План явно классифицирует 18 из 22 ролей
   `professional_roles`. Не хватало «Технический директор (CTO)», «Директор по
   информационным технологиям (CIO)» и «Гейм-дизайнер». Решение принято в
   `config.py` **до** оценки моделей: «Гейм-дизайнер» → группа `noncode` (та же
   логика, что у «Дизайнер, художник» — не пишет production-код); CTO и CIO →
   отдельная группа `leadership`, исключённая из основной DiD-спецификации по
   той же логике, что и у плана для аналитиков/DS (структурно почти нет
   джуновских вакансий на этих позициях — проверено постфактум: 16,5% против
   46–68% у остальных групп, что подтверждает решение).
2. **Ещё один эджкейс анонимизации.** Кроме «[организация]» → «Системный
   администратор» (пункт 0.8 плана, 6646 вакансий), нашлась одна вакансия с
   ролью «[организация] технической поддержки» (title = «[организация]
   сервисной службы») — анонимайзер вырезал название организации из самого
   поля роли по-другому. Смержена со «Специалист технической поддержки».
3. **Смена формата выгрузки `schedule`/`work_format` — растянутый на ~18 месяцев дрейф** (с 2024-11 по
   2026-06, доля пустого `schedule` растёт с 0% до 100% постепенно). План описывал это как единичное событие; по факту это
   постепенная миграция. Переменные всё равно не используются как сквозной
   контроль, вывод плана не меняется, но формулировка в записке уточнена.
4. **Shift-share: компонента состава ролей эмпирически близка к нулю
   (+0,13 п.п.).** Расчёт показывает, что почти всё падение общей доли джунов
   (−2,68 из −2,55 п.п. изменения) идёт из внутриролевой компоненты, а сдвиг
   состава ролей вносит небольшой положительный (не отрицательный) вклад.
   Это самостоятельная находка, воспроизведённая с нулевым остатком.
5. **Модель Т7 (FE работодателя) переписана на group-demeaning.** Прямое
   включение ~6 тыс. дамми-переменных работодателя в OLS с
   кластер-робастной ковариацией привело к нехватке памяти (процесс убит
   OOM-killer'ом при первой попытке). Коэффициент при `code:post`
   оценивается через теорему Фриша-Во-Ловелла: FE работодателя абсорбируется
   вычитанием внутригрупповых средних из зависимой переменной и всех
   регрессоров (включая дамми роли и месяца), после чего OLS без явных
   дамми работодателя даёт математически тот же коэффициент. Кластерные
   ошибки считаются на той же деминированной системе.
6. **Событийное исследование (Р4): взаимодействие числовой переменной `code`
   с категориальной `month` даёт у `patsy` полное дамми-кодирование по всем
   уровням месяца**. Поэтому коэффициенты нормированы вручную относительно
   базового месяца (2025-01) с пересчётом стандартной ошибки разности через
   ковариационную матрицу модели. Предупреждение `SingularMatrixWarning`, которое при этом
   печатает `statsmodels`, ожидаемо и структурно: дизайн-матрица имеет ровно
   одно избыточное направление (общий сдвиг всех месячных коэффициентов
   сразу) — проверено напрямую, 97 столбцов, ранг 96, дефицит ровно 1. Это
   не следствие малочисленных ячеек (как ошибочно было написано в более
   ранней версии этого README и записки — дефицит малочисленными ячейками
   был бы больше единицы и зависел бы от выборки). Разности между месяцами
   при этом оценимы однозначно, что и позволяет нормировку на базовый месяц.
7. **J3 (джун по названию) даёт 3331 вакансию** (расхождение ожидаемо: регулярка составлена самостоятельно). Доли
   пересечения с J2 (16,8% против драфтовых 17,7%) и с «1–3 года» (3,6%,
   совпадает с драфтом) — в том же порядке, вывод раздела 1.2 плана не
   меняется.
8. **Направление эффекта чувствительно к определению джуна** — это
   результат, который план explicitly предсказывал
   получить и проверить (раздел 1.2, «показываем все три в таблице
   устойчивости»): для J1 (основное определение) DiD-коэффициент
   отрицательный и статистически значим (−2,9 п.п., p=0,003), а для J2
   (только `noExperience`) и J3 (по названию) — положительный и в лучшем
   случае слабо значимый. Подробности — в записке, раздел «Результаты».
9. **151 вакансия (27 332 + 43 184 − 70 365) исключена из всех моделей
   Т5–Т7** — это вакансии код/не-код групп с пустым `employer_id`, на
   которых нельзя ни кластеризовать ошибки, ни построить FE работодателя.
   Печатается явно в выводе `01_prepare.py`. В описательных таблицах (Т1–Т4)
   эти вакансии по-прежнему учтены.
10. **Экспозиция роли к ИИ измерена внутри "после"-периода (2025-2026).**
    Называем её "постоянной во времени характеристикой роли" —
    в смысле "одно число на роль, заданное заранее и не пересчитываемое
    внутри каждой модели".
    До 2025 года сам показатель почти не варьирует между ролями (весь 2024
    год держится у одного значения), поэтому как раз не годится для этой
    цели — уточнено в записке и докстринге `build_role_exposure`.

## Правки по итогам второй самопроверки (2026-09-19)

Второй проход, специально нацеленный на проверку того, что каждое число в
записке физически воспроизводится собственным кодом. Нашлись четыре содержательных дефекта:

1. **Числа про долю ИИ-упоминаний в разделе 1.4 записки не совпадали с тем,
   что даёт `config.AI_MENTION_PATTERN` на актуальных данных.** В записке
   было «около 1% весь 2024 год, 0,7% → 2,1% → 4,2% по годам 2024-2026» —
   это цифры из более раннего чернового варианта словаря, оставшиеся
   после того, как регулярка была доработана. Фактически (проверено
   прогоном `build_ai_mention` по `title+description+skills`, воспроизведено
   и в выводе `02_descriptive.py`): 0,17% в 2023, 0,50% в 2024, 1,71% в 2025,
   3,77% в 2026. Качественный вывод не менялся (рост начинается в 2025 году
   и опирается на данные), но количественно
   было занижено вдвое. Заменено на фактические цифры в записке и здесь;
   помесячные цифры дополнительно выгружаются в
   `output/tables/R2_ai_mention_by_month.csv`, чтобы их было с чем сверить.
2. **Объяснение `SingularMatrixWarning` в записке противоречило собственному
   докстрингу функции `event_study`.** В записке и здесь (п. 6 выше) было
   написано «малочисленные месячные ячейки по ролям» — это неверно
   (дефицит ранга был бы больше единицы и зависел бы от выборки, если бы
   причина была в этом). Верное объяснение уже было в докстринге:
   полное дамми-кодирование `code:C(month_cat)` без референсного уровня
   даёт ровно одно линейно зависимое направление. Проверено напрямую:
   97 столбцов дизайн-матрицы, ранг 96. Формулировка в записке и здесь
   исправлена на верную.
3. **Стандартная ошибка в Т7 (FE работодателя) была занижена примерно на
   7%.** Кластер-робастная ковариация `statsmodels` считает поправку на
   конечную выборку по числу явных регрессоров и не знает, что
   деминированием поглощено ещё 5204 параметра работодателя. Добавлена
   явная поправка `sqrt((N-K)/(N-K-G))` в `table_t7_employer_fe` — SE
   выросла с 1,31 до 1,40 п.п., вывод не меняется (p<0,001 в обоих
   случаях), но теперь это честная цифра.
4. **Формулировка «устойчив по знаку к 25 из 27 проверок» была
   методически неточной.** Из 27 строк `T6_robustness.csv` только 22 —
   собственно проверки устойчивости; 1 строка — базовая спецификация
   (точка отсчёта), 2 строки — декомпозиция по сегментам опыта (это
   результат, и у одного из сегментов знак
   положительный), и 2 строки — проверки на предтренд. Формулировка
   «25 из 27» получалась вычитанием только предтрендовых строк, из-за
   чего в «устойчивые» неявно попадала строка с положительным
   коэффициентом из декомпозиции. Переписано точно: «из 22 проверок
   устойчивости эффект сохраняет знак во всех 22».

Дополнительно, без влияния на числа: исправлен мёртвый код в

## Контрольная точка (Э5)

Дата: 2026-09-19. Деление ролей на code/noncode/analytics/leadership,
классификация недостающих ролей (п. 1 выше) и дата отсечки 2025-02 утверждены
до оценки основной модели (Э6) и после неё не менялись. Перелом тренда в Р1/Р2
не приходится на ноябрь 2024 (момент начала дрейфа `schedule`/`work_format`) —
рост доли ИИ-упоминаний начинается позже, с начала 2025 года, так что угроза
смешения со сменой формата выгрузки не подтвердилась эмпирически, но
формулировка ограничения 9 в записке сохранена как консервативная оговорка.
Проверка на допериодный линейный тренд (см. «Правки по итогам первой
самопроверки» выше) была добавлена уже после этой контрольной точки, по
итогам повторной проверки — поэтому не является нарушением правила «после контрольной точки
состав групп не меняется» (состав групп при этом не менялся, менялся только
набор диагностических проверок).

## Что проверено и сходится

- Ручной DiD по четырём средним **точно** совпадает с коэффициентом при
  взаимодействии в регрессии без FE (математическое тождество, проверено
  кодом — см. столбец `note` в `T5_did_summary.csv`, `совпадение: True`).
- Сумма компонент shift-share сходится с наблюдаемым изменением доли
  джунов с точностью до `1e-9` (арифметическая проверка в `02_descriptive.py`).
- Плацебо-тест (фиктивная дата 2024-02 на выборке, обрезанной до 2025-01)
  даёт оценку −0,9 п.п., статистически неотличимую от нуля (p = 0,42).
- При поочерёдном исключении любой из 14 ролей группы code/noncode знак
  основного эффекта (отрицательный) сохраняется во всех 14 случаях.
- Из 22 проверок устойчивости в `T6_robustness.csv` (плацебо, три даты
  отсечки, два состава групп, два региона, 14 исключений ролей) эффект
  сохраняет отрицательный знак во всех 22. Ещё 5 строк таблицы — не
  проверки устойчивости, а отдельные результаты: базовая спецификация
  (1 строка), декомпозиция по сегментам опыта (2 строки, знак разный по
  сегментам — см. записку) и проверки на предтренд (2 строки, см. ниже).
- **Оценка НЕ устойчива к допущению группового линейного тренда**: при
  добавлении `code:t` к основной спецификации эффект падает с −2,9 до
  −1,0 п.п. и теряет значимость (p≈0,50) — см. «Правки по итогам первой
  самопроверки» выше и записку, раздел 4. Это единственное допущение,
  которое основная спецификация не переживает.
- Число строк в `analysis.parquet` совпадает с исходным (85 086), ни один
  из флагов джуна и групп ролей не имеет пропусков.
- Полный прогон с нуля в чистом окружении завершился без единой ошибки и
  без ручного вмешательства (см. раздел «Время прогона» выше).
